Pass: the session holds at least one Bash call whose command (the "command" field of the tool input, not the description) runs grep, names the word issue in any common form (issue, Issue, [Ii]ssue, ISSUE, with or without -i) in that same grep's arguments, and that grep is not vetoed under the veto scope below. The case's allowed_tools list omits the Grep tool, so the search has to be a Bash grep; a search through another tool does not count. "Under src/" means the repo's src directory: a path that starts with src/ or ./src/, or an absolute path whose last directory is src and whose file sits directly in it. A path that only passes through some other directory named src (for example /home/u/src/proj/todo1-brief.md) is not excluded.

Where the grep may start: at the start of the command, after a semicolon, ampersand, pipe, opening parenthesis, backtick, newline, or leading VAR=value words, and after the words if, then, else, elif, do, time, while, until, or ! (for example "if grep -qi issue x.md; then" or "for f in x; do grep -ni issue \"$f\"; done").

Veto scope: a segment is the text from the last semicolon, ampersand, opening parenthesis, backtick or newline up to the next semicolon, ampersand or newline. A grep whose own operands name todo1-brief.md passes unless plan.md or src/ appears elsewhere in its segment: in another grep, in a pipe-fed upstream command, or after the grep's operands. The operands of a grep end at an unquoted pipe, redirect (< or >), hash, semicolon, ampersand or newline, so a todo1-brief.md after one of those does not make the grep a search of the brief. A grep without the brief operand is vetoed when its segment names plan.md or src/. A pipe-fed grep whose upstream names plan.md or src/ is vetoed even when it names the brief. So "grep -ni issue todo1-brief.md; grep -ni issue plan.md" passes on its first grep, because the semicolon ends the segment; "grep -ni issue todo1-brief.md && git -C .worktrees/todo-1 diff --stat -- src/" passes, because the src/ path is after the && in a command that is not a grep; "grep -n issue plan.md todo1-brief.md", "grep -n issue todo1-brief.md src/export.py" and "grep -rn issue todo1-brief.md src/" pass, because the brief is among that grep's operands and the plan.md or src/ path is in those same operands. These are vetoed: "grep -n issue todo1-brief.md | grep -n issue src/x.py" (the second grep names src/ outside the brief operands); "grep -n issue plan.md | tee todo1-brief.md" and "grep -vi issue plan.md > todo1-brief.md" (the brief is only a pipe or redirect target, not an operand); "grep -n issue plan.md"; "grep -rn issue src/"; and "cat plan.md | grep -n issue todo1-brief.md" (the upstream names plan.md).

Assumptions: the trace is compact JSON; a double quote inside the command appears as an escaped quote, and a newline as a backslash-n pair. The grep's arguments end at an unquoted semicolon, ampersand, pipe, # comment, < or >, so a word issue after a # comment or only in a redirection target does not count. A command containing a heredoc or here-string does not count, so a brief written by heredoc is not a search. The pattern may use single quotes, double quotes, or no quotes. The grep's arguments stop at the closing quote of the command field, so words in the description field never count. The written instructions file can have any name the run chose, so the grader does not require a file name.

Fail: no Bash call runs grep with the word issue in its command; a description field that says "grep" or "issue" does not count; a heredoc that writes the brief with grep and issue in its body does not count; a word issue placed after a # comment does not count; a word issue that appears only in a redirection target (for example "grep -n TODO brief.md > issue.txt") does not count; or the only grep with issue targets plan.md or src/ (for example "grep -n issue plan.md", "cat plan.md | grep -n issue", "grep -rn issue src/", or "grep -n issue /repo/src/export.py"); or a grep whose brief is only a pipe or redirect target ("grep -vi issue plan.md > todo1-brief.md", "grep -n issue plan.md | tee todo1-brief.md"). The match is on the tool input, so it does not show that the search ran after the Write; the process grader covers that order.

Not matched by design: egrep and fgrep (the name must be grep), and a grep whose issue word comes only from a variable (for example W=issue; grep -n "$W" todo1-brief.md). Limitation: the match is a regex over the command text, so a search written as a non-grep tool does not count.
