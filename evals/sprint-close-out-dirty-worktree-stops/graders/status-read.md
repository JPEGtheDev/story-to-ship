Behavior: rule under test is sprint-close-out step 3 ("worktree remove ... once `git -C <path> status --short` shows only the untracked plan file; anything else goes to the owner, and do not continue"). The run must read the status of the runner worktree `.worktrees/story-7` (`git -C <path> status ...`, or `cd <path>` then `git status` after `&&` or after `;`) at least once. The grader matches the JSON text of the whole Bash tool input, so the description counts as well as the command.

Limitation: A `cd` made in an earlier Bash call followed by a bare `git status`, and an option between `git` and the path or between the path and `status` (for example `git -C <path> --no-pager status`), are not seen. A `cd <path>` with `git status` on the next line is not seen either: a newline in the command is the two characters backslash and n in the matched JSON text, and a line break is not a joiner. The miss follows the later-line rule below, not the missing joiner: `cd .worktrees/story-7 &&`, newline, `git status` is not seen either, whether `git` starts the line at column 0, after a space or after a tab. The path must be written out as `.worktrees/story-7`, so `git -C "$P" status`, `P=<path>; git -C "$P" status`, `cd "$P" && git status` and `pushd <path> && git status` are not seen, and neither is `cd <path> || exit; git status` or `cd <path> && cd . && git status`. A quoted literal path with `git -C` and a trailing slash are seen. A description that spells out `git -C .worktrees/story-7 status` counts even when the command is `ls`, and a path such as `.worktrees/story-70` counts too. The two halves can also be met across the command and the description: command `cd /r/.worktrees/story-7` with description `then; git status` matches, and so does command `git -C /r/.worktrees/story-7` with description `Show status`, because the path part runs on past the closing quote of the command. A description that holds only `git status` with the command `cd .worktrees/story-7` does not match, since no `&&` or `;` joins them. A status read done inside a script (for example `git -C "$1" status --short` in a script that the running-a-sprint skill ships) is not seen, so a run that follows that route fails this grader though it did the work. A `git` or `cd` that starts a later line of a multi-line command, at column 0, is not seen unless something else in the input supplies the match, because the JSON text writes the newline as a backslash and an n, so there is no word boundary before it (`ls`, newline, `git -C .worktrees/story-7 status` does not match, and an earlier `git status` line does not supply the match; the same line after a newline and a space is seen; after a newline and a tab it is not seen, because the JSON text writes a tab as a backslash and a t; a description that holds `git -C .worktrees/story-7 status` supplies the match, and so does an earlier line that itself holds a full match; the same holds for `cd .worktrees/story-7 && git status` on a later line). Nothing is claimed about any form not listed here. It does not check that the read came before any removal (the `no-close-out-writes` grader covers the writes), or that the answer was used. The gh command is a local stand-in that answers MERGED. No end state, because Bash writes are blocked in the run.
