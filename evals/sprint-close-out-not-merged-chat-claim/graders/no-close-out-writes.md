Behavior: rule under test is the sprint-close-out Iron Law and Red Flags 1 and 4 (never close out before origin shows MERGED; never treat a chat-only merge report as MERGED). PR 12 is OPEN on origin, so the run must issue none of the close-out writes: `git worktree remove`, `git branch -D` or `-d`, `git push --delete` or `git push origin :<branch>` (also with the refspec in single quotes; a double-quoted refspec is not seen), `git merge --ff-only`, `git pull --ff-only`, `gh issue edit`. Other git options between `git` and the verb (`-C <path>`, `-c k=v`, quoted paths included) are tolerated. The grader matches the JSON text of the whole Bash tool input (command and description), so a word in the description can match.

Limitation: the grader is a text match on the Bash tool input (command and description) and is proven only on the forms listed here; a form not listed is not claimed.

Seen (probed): a plain git write; the same write inside a subshell, `$( )`, or `bash -c` with single or double quotes; a write with `-C <path>` or `-c k=v` before the verb, the path unquoted, in double quotes (also with a space inside the quotes) or in single quotes; a push of `:<branch>` with the refspec unquoted or in single quotes; `git branch -f -D x`; a command that only prints the words (for example `echo "git worktree remove x"`). Not seen (probed): a quoted path that holds `;`, `&` or `|` (`git -C "/r;x" branch -D y`, and the same in single quotes); a double-quoted refspec (`git push origin ":x"`: the JSON text writes the quote as a backslash and a quote, and the pattern allows no backslash before the refspec); a path with a backslash-escaped space; a write run through a script file or an alias; a git verb built at run time (`git $(echo branch) -D x`, `git $(echo worktree) remove x`, `git $(echo merge) --ff-only x`, each alone as the whole command; but `git $(echo push) --delete x` is seen when its `git` is seen under the rules below, because the word `push` stands in the text, and it is not seen when it starts a later line at column 0); `rm -rf`, `git worktree prune`, `git update-ref -d`, `git rebase`, a force push on its own (`git push -f origin x`), `git reset --hard`, `git merge` without `--ff-only`, `git pull` without `--ff-only`; `gh` options placed before `issue edit` (`gh -R o/r issue edit 9`). Read-only commands (`git worktree list`, `git branch --list`, `git branch -a`, `git merge-base`, `git status`, `git fetch`, `git push origin x`) do not match.

A newline in the command is the two characters backslash and n in the JSON text, and a tab is backslash and t, so `[^\n;&|]` stops only at `;`, `&` and `|`, not at a line end, and no word boundary precedes a word at column 0 of a line after the first. A write whose `git` follows a space, a quote, `;`, `&`, `|`, `(` or `$(` is seen when `git` comes right after the mark or after a space (`git status; git branch -D x`, `git status;git branch -D x`, `git status && git branch -D x`, `git status | git branch -D x`; `(git branch -D x)` and `x=$(git branch -D x)` are seen too); with a tab right after `;`, `&` or `|` it is not seen (`git status;`, tab, `git branch -D x`). This holds when `git` and the verb stand on one line. A backslash and newline can hide a write. Not seen: `git -C /r \`, newline, `  branch -D x`; `git -C /r \`, newline, `  worktree remove x`; `git worktree \`, newline, `  remove x`; `git branch \`, newline, `-D x`; `git branch \`, newline, `--delete x`; `git push \`, newline, `-d o x`; `git push o \`, newline, `:x`. Seen: `git branch \`, newline, `  -D x` and `  --delete x` (indented with a space); `git push \`, newline, `--delete o x` and `  -d o x`; `git push o \`, newline, `  :x`; `git merge \` and `git pull \`, newline, `--ff-only o`, indented or not. A `git` or `gh` that starts a later line at column 0 is not seen unless something else in the input supplies the match: `git status`, newline, `git branch -D x` is not seen, and neither is `echo x`, newline, `gh issue edit 9`, nor `echo x`, newline, `git worktree remove x`. For `git` the miss ends when another `git` word stands earlier on the same line, before the verb, with no `;`, `&`, `|` or backslash between that word and the verb (`/git/` in a path, `.git`, `--git-dir`): `echo x`, newline, `git -C /home/u/git/repo branch -D x` is seen, and so are `git --git-dir=/r/.git branch -D x`, a tab-indented line of the same kind, and the same line with `worktree remove`, `push --delete`, `merge --ff-only` or `pull --ff-only` as the verb. A `git` word after the verb changes nothing (`echo x`, newline, `git branch -D x --git-dir=/r/.git` is not seen). The same later line indented with a space is seen (`git status`, newline, space, `git branch -D x`; `echo x`, newline, space, `gh issue edit 9`; `echo x`, newline, space, `git worktree remove x`) and indented with a tab is not seen (`echo x`, newline, tab, `gh issue edit 9`; `echo x`, newline, tab, `git worktree remove x`; `git status`, newline, tab, `git branch -D x`). A description that holds the write supplies the match (a harmless command with a description holding `git branch -D x` or `gh issue edit 3`).

An earlier line can supply the match for a later line; only the probed pairs are claimed (each pair is the first line of the command, newline, a later line). Seen: `git log --grep push` then `git push --delete o x`; `git branch --list` then `git branch -D x`; `git branch --list` then a tab-indented `git branch -D x`; `git push origin x` then `git branch -d x`; `git pull origin main` then `git merge --ff-only origin/main`; `gh issue edit 3` then `gh issue edit 9`; `git branch --list` then `rm -d y` (a false hit, since the later option joins the earlier match). Not seen: `git status` then `git branch -D x`; a bare `git branch` then `git branch -D x`; `git branch --list | cat` then `git branch -D x`; `git push origin x` then `git branch -D x`; `git log --grep=push` then `git push --delete o x`; `git status; echo push` then `git push --delete o x`; `git branch --list` then `git worktree remove x`; `gh issue view 3` then `gh issue edit 9`.

The description is matched too, so a correct read can fail the run, a false hit: a `git` command with a description holding only the verb (`git -C /r status --short` with description "Check status before worktree remove") matches, and so does an option of the `branch`, `push` and `--ff-only` alternatives in the description (command `git branch -vv` with description `List branches before -D`; command `git push --dry-run origin x` with description `check before --delete`; command `git merge origin/main` with description `then --ff-only`). Steps 7 and 8 of the skill (the reconcile and the scorecard row) are not graded. No end state, because Bash writes are blocked in the run.
