---
type: tool_order
before:
  tool: Bash
  input_match: '\bgh\s+pr\s+view\s+12\b'
after:
  tool: Bash
  input_match: '\bcmp\b|\bdiff\b[^\n;&|]*<\([^\n]*<\('
---

Behavior: rule under test is the sprint-close-out steps-in-order rule (Iron Law, BEFORE PROCEEDING item 2): step 1 reads origin with `gh pr view 12`, then step 2 compares the patch of the runner branch with the patch of the squash commit (`cmp` or `diff` of the two patches). The first origin read must come before the first patch comparison.

Limitation: it grades steps 1 and 2 only; steps 6 to 8 and the lane_sum count are ignored. It fails if either command is never run, and a single chained command counts as one position, so a read and a comparison in one command do not pass. It does not check the comparison was correct. A patch comparison written as two plain `git diff` calls, or made with `git range-diff` or `git patch-id`, is not counted unless it is wrapped in `cmp` or `diff <(...) <(...)` (`diff <(git diff a b | git patch-id) <(git show S | git patch-id)` is counted), and the `git diff --numstat` lane count is not mistaken for a comparison. Both patterns run on the JSON text of the whole Bash tool input (command and description), so a word in the description can match: `echo hi` with description "gh pr view 12" counts as the read, and `git diff --numstat a b` with description "compare with cmp" counts as a comparison (plain `git diff --numstat a b` does not). The read pattern needs `gh pr view 12` as adjacent words: `gh pr view 12 --json state,mergeCommit` and `gh pr view 12 -R o/r` count (probed true), while `gh pr view --json state,mergeCommit 12`, `gh pr view -R o/r 12`, `gh -R o/r pr view 12` and `gh api repos/o/r/pulls/12` do not (probed false), so such a read is not counted as the origin read unless the description supplies the words. A newline in the command is the two characters backslash and n there, so `[^\n]` in the `diff <(` pattern crosses lines, and no word boundary precedes a `gh`, `cmp` or `diff` at column 0 of a line after the first (`\ngh` reads `ngh`), so such a word is not seen on its own. A line indented with a space is seen; a line indented with a tab is not (the JSON text writes a tab as a backslash and a t). The miss holds only when nothing else in the input supplies the match: the description can supply it, and an earlier line that holds a match of its own counts. For `diff <(..) <(..)`, an earlier line holding a `diff` also supplies it, because the `[^\n;&|]*` tail runs on past the backslash and n (`git diff a b` newline `diff <(a) <(b)` matches; after a `;` ending that line it does not). Every earlier-line form in this file assumes the earlier line is itself seen, as the first line or after a space; an earlier line whose needed word (the `git`, `gh`, `cmp`, `diff` or `rm` of that form) stands at column 0 of a line after the first is not seen and supplies nothing by itself, while the same word later in that line, after a space, is seen. No end state, because Bash writes are blocked in the run.
