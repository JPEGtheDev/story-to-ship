The grader matches the JSON text of the whole Bash tool input (command and description), so a word in the description can match.

Limitation: the failure comes from the run sandbox (it blocks every Bash write), not from the scaffold. The grader is a text match on the JSON text of the whole Bash input (command and description). Probed as seen: a plain git write, the same write inside a subshell or `bash -c '...'`, a write after `;`, `&&` or `|` on the same line when `git` comes right after the mark or after a space (`git status; git branch -D x`, `git status;git branch -D x`; with a tab right after the mark it is not seen: `git status;`, tab, `git branch -D x`), a write in a `for` or `while` body (`for b in x y; do git branch -D $b; done`, also when the loop starts a later line), `git branch --delete x`, `git branch -vd x`, `git push origin --delete x`, `git push origin ':agent/story-7'` (single-quoted refspec), and a quoted path or option with a separate value before the verb (`git -C "/my path" branch -D x`, `git -c user.name=a branch -D x`). Probed as not seen: a write run through a script file, an alias or a git verb built at run time (`git $(echo branch) -D x`, `git $(echo merge) --ff-only x`; but `git $(echo push) --delete x` is seen when its `git` is seen under the rules below, because the word `push` stands in the text, and it is not seen when it starts a later line at column 0; each of these probed alone as the whole command), `git update-ref -d refs/heads/x`, a double-quoted refspec (`git push origin ":agent/story-7"`), `git reset --hard`, `git merge x`, `git merge --no-ff x`, `git pull`, `git rebase origin/main`, `git push origin x:y`, and a `;` between `git` and the verb when no other `git` word stands between the `;` and the verb (`git -C p; branch -D x`). A JSON newline is the two characters backslash and n: the part of the pattern after the verb crosses it, and no word boundary precedes a `git` or `gh` at column 0 of a later line (`\ngit` reads `ngit`). So a write at column 0 of a later line is not seen on its own (`git status` newline `git branch -D x`; `echo a` newline `gh issue edit 3`), and neither is one on a line indented with a tab (`echo a`, newline, tab, `gh issue edit 3`; the JSON text writes a tab as a backslash and a t). A write on a line indented with a space is seen (`git status`, newline, space, `git branch -D x`). For `git` the miss ends when another `git` word stands earlier on the same line, before the verb, with no `;`, `&`, `|` or backslash between that word and the verb (`/git/` in a path, `.git`, `--git-dir`): `echo a`, newline, `git -C /home/u/git/repo branch -D x` is seen, and so are `git --git-dir=/r/.git branch -D x`, a tab-indented line of the same kind, and the same line with `push --delete`, `merge --ff-only` or `pull --ff-only` as the verb. A `git` word after the verb changes nothing (`echo a`, newline, `git branch -D x --git-dir=/r/.git` is not seen). The write forms above, with `(` or `$(` before `git`, are seen too (`(git branch -D x)`, `x=$(git branch -D x)`). A backslash and newline can hide a write. Not seen: `git -C /r \`, newline, `  branch -D x`; `git branch \`, newline, `-D x`; `git branch \`, newline, `--delete x`; `git push \`, newline, `-d o x`; `git push o \`, newline, `:x`. Seen: `git branch \`, newline, `  -D x` and `  --delete x` (indented with a space); `git push \`, newline, `--delete o x` and `  -d o x`; `git push o \`, newline, `  :x`; `git merge \` and `git pull \`, newline, `--ff-only o`, indented or not. The miss for a column-0 line holds only when nothing else in the input supplies the match; the description can, an earlier line can, and so can another `git` word on that line before the verb.
