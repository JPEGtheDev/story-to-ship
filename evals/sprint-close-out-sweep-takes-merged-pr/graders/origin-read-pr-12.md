Behavior: rule under test is the sprint-close-out start rule (description: the close-out starts when a sweep of origin finds a merged sprint pull request, as well as when the owner reports one; Iron Law: confirm the merge on origin). The sweep reads origin state for PR 12 at least once: `gh pr view` naming 12 (any flags, any repo option), any `gh pr list` command, or `gh pr view` inside a `for ... in` loop over numbers that include 12 (`; do` on the loop line).

Limitation: The grader matches the JSON text of the whole Bash tool input (command and description), not the command alone, so a word in the description can match; a newline in the command is the two characters backslash and n there, so `[^\n]` does not stop at a line end, and the first word of a later line at column 0 has no word boundary before it (`\ngit` reads `ngit`), so `\bgh` misses it there when nothing else in the input supplies the match. The text writes the newline as a backslash and an n; a line indented with a space is seen, and a line indented with a tab is not (it writes a tab as a backslash and a t); the description can supply the match (`echo a` with description "gh pr view 12" matches); and an earlier line that holds a `gh` with no `;`, `&` or `|` after it, such as a first `gh pr view 13 --json state` or a `gh auth status` (neither matches alone), starts the match at that earlier `gh`, so the tail runs on past the backslash-n and the later line is covered too, even a tab-indented one, whereas `gh auth status; echo` then a column-0 `gh pr view 12` is not seen. Any `gh pr list` command counts, whatever it lists or filters, and a loop counts when it is written `for NAME in LIST`, its list includes 12, `; do` follows on the same line, and a `gh pr view` stands later in the input text on the same line, on a later line indented with a space, or in the description; a `gh pr view` at column 0 of a later line or on a tab-indented later line does not count (`for n in 12 13; do x=1; done` then `gh pr view $n` at column 0 or after a tab does not match, after a space it does). A `while read` loop (`printf '12\n13\n' | while read n; do gh pr view "$n" --json state; done`) and a C-style loop (`for ((n=12; n<=13; n++)); do gh pr view $n --json state; done`) do not match. Reading only PR 13 can pass: `gh pr view 13` with description "Check PR 13 after PR 12" matches, and so does `gh pr view 13` followed on the next line by `echo 12`; `gh pr view 13` alone does not. A non-gh command whose description says "gh pr view 12" also matches. A list command that never reaches PR 12 is not told apart. A loop with `do` on its own line is not seen unless the description also names 12 (then the `gh pr view` in the command matches through it, but only when no `;`, `&` or `|` follows that `gh pr view` in the command); a loop written across several statements or through a variable list is not seen on the same terms (`L="12 13"`, `for n in $L`, `do`, `  gh pr view $n`, `done` on separate lines matches with description "Read PRs 12 and 13" and does not with "Read PRs", nor when a `;` follows the `gh pr view $n`); a `gh` at column 0 of a later line is not seen when nothing else in the input supplies the match (see above). `gh api` reads of PR 12 (`gh api repos/o/r/pulls/12`) do not count. A read through a shell variable (`PR=12; gh pr view "$PR" --json state`) and an `xargs` read (`echo 12 13 | xargs -n1 gh pr view`) are not seen either (probed: both give no match). It does not check that the answer was used. The gh command is a local stand-in that answers MERGED for 12. No end state, because Bash writes are blocked in the run.
