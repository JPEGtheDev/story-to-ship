Behavior: the run ignores `.worktrees` before its first `git worktree add`, by either route: (a) a Bash write to the repository-root `.gitignore`, or (b) a Bash write to `.git/info/exclude`. A write is a `>` or `>>` redirect; `tee`, after any short (`-a`) or long (`--append`) or bare `--` option; or `sed -i`, in one command that also names `.worktrees` before any `worktree add` in that command. The write passes when it is in a command that comes before the first `git worktree add` command, or when it comes first in a chain with that add (`echo .worktrees >> .git/info/exclude && git worktree add ...`). The written file must be `.gitignore` or `.git/info/exclude` itself: it must start the command or follow whitespace, a quote, `=`, `>`, `|`, `&`, or `;`, with an optional `./` prefix (`>> ./.gitignore` names the root file). A path with any other character directly before it (`.worktrees/.gitignore`, `/tmp/x/.gitignore`, `$(git rev-parse --show-toplevel)/.gitignore`, `a.gitignore`) does not match, and neither does one followed by more name characters (`.gitignore.bak`, `.git/info/excluded`), so that run fails. A command that only reads these files (grep, cat), only runs `git check-ignore`, or only redirects stderr (`2>&1`) does not match, so it fails, even when the skill's own check line prints the instruction. A write counts only when no `cd` word comes before it in the same command, including a bare `cd`, a `cd` followed by whitespace, `;`, `&`, or an escaped tab or newline, and a `cd` that starts a new line or follows a tab: `cd .worktrees && echo '*' > .gitignore` writes `.worktrees/.gitignore`, not the root file, so it fails. The `sed -i` form has the same `cd` rule and also stops at a command separator: a `cd` word, a `;`, `|` or `&`, or an escaped newline between the `sed -i` and the file name means the file is not its target, so `sed -i 's/a/b/' README; cd .worktrees && echo '*' > .gitignore` and `sed -i 's/x/y/' plan.md; grep -q .worktrees .gitignore` do not match, while `sed -i '$a .worktrees' .gitignore` does. The rule is blunt: a root write that follows any `cd` in the same command (`cd .. && ...`, a subshell, a later chain step) also fails, a false fail. Limits: a `pushd` before the write is not treated as a `cd`, so that write still passes; a write that comes after the add in the same command, or in a later command, fails; an edit made with a tool other than Bash is not matched (the case allows only Bash for this step); a write to any other file is not matched; an absolute path to the repository root (`/repo/.gitignore`) is not matched. The check is a command-form match, so no judge is needed.

Limitation: a `sed -i` whose script holds a `;`, `|` or `&` (`sed -i 's/a/b/;s/c/d/' .gitignore`, `s/a/&b/`) is not matched, a false fail. The `sed -i` branch does not parse the sed script or options, so a `sed -i` that leaves the file unchanged still counts. The pattern anchors with `^` and assumes the engine sets no multiline flag; that is unconfirmed. It also assumes compact `"command":"` JSON (no space after the colon) and needs an engine that supports negative lookbehind and lookahead; that is unconfirmed too. It does not check that the write succeeded.
