---
type: regex
pattern: '^(?:(?!"name":"Agent")[\s\S])*"id":"(toolu_\w+)","name":"Bash","input":\{"command":"(?:[^"\\\n]|\\.)*worktree add(?:[^"\\\n]|\\.)*"(?:(?!"name":"Agent")[\s\S])*?\{"tool_use_id":"\1","type":"tool_result","content":(?!"Exit code)[\s\S]*?"name":"Agent"'
match: contains
target: trace
---

Behavior: the run runs a `git worktree add` command in Bash that succeeds before its first Agent call. The pattern decides success by key order and the `Exit code` prefix only: the `tool_result` object with the same `tool_use_id` must start with `tool_use_id` (before `type`), must come before the first Agent call, and its content must not start with `Exit code`. It does not read `is_error`: a result with `"is_error":false` is not rejected and passes, as does any `tool_use_id`-first result. In the observed traces a failed Bash call has the key order `type, content, is_error, tool_use_id` with `is_error` true and content starting `Exit code N`, and a successful call has `tool_use_id` first (six such results in the scratch sample traces carry `"is_error":false`, none carry `"is_error":true`); the pattern matches the successful form. The pattern is escape-aware, so a quoted path such as `git -C \"/a/b\" worktree add` is matched. It does not check where the dispatch goes; the paired grader dispatch-names-worktree checks that the dispatch names a `.worktrees/` path. The check is a command-form match, so no judge is needed. Limitation: any command text that contains `worktree add` and succeeds passes, so an `echo` mention passes; a `tool_use_id`-first failure whose content does not start with `Exit code` (for example `"is_error":true` with content `fatal: x`) would also pass; the pattern assumes no multiline flag (confirmed: the harness config sets `"flags": ""`, so `^` anchors only at the start of the trace), compact JSON, and the observed key order (`"id"` then `"name"` in a tool call, `tool_use_id` first in a successful result), so a trace with another order fails even when the run is correct.
