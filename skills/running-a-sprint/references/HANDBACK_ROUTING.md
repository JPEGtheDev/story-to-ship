# Hand-back routing table

This file is the launcher's routing table for a sprint. Each runner is a coordinator subagent (the story-coordinator template) that runs one story and hands back; the launcher is the session that started the runners, relays the owner's answers, resumes runners, and closes out merges. A child is a subagent a runner dispatched, never the runner itself. Read this file whenever a hand-back or a runner event arrives, before acting on it.

**Context:** A hand-back or event arrives while other runners are still working, and the quickest reply looks like answering the runner directly.
**Forces:** The launcher holds the owner's attention and the runners' branches, while a runner holds only its own story, so every reply that is not a lookup in this table risks a decision the owner never made. The owner-reserved decisions are exactly: merge, fix-round cap override, scope change.

Every cell in the Launcher must NOT column starts with the same four prohibitions, and each row adds its own after them.

| Hand-back or event | How the launcher recognizes it | Launcher response | Launcher must NOT |
|---|---|---|---|
| **owner question** | The first line of the hand-back reads "owner question"; it lists options and a recommendation. | Relay the question to the owner with the options and the runner's recommendation, record it as the pending question in the sprint ledger (the launcher plan file), and end the turn; when the owner answers, resume the runner with the answer. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; answer the question from earlier rulings; resume the runner before the owner answers; |
| **PR ready** | The first line reads "PR ready"; the hand-back names the pull request number, the continuous integration (CI) state, and the review verdicts. | Re-run gh pr view yourself for the pull request number and CI state, check the required lines, run the inline-edit comparison (a runner cannot read the inline-edit guard's ledger, the hook's record of inline edits, so compare the lane entries in its plan file, each todo's record of its route written as lane: dispatch or lane: inline with a line count and a file name, with git diff --numstat over the runner's inline commits, where a replaced line counts 2, and report any mismatch to the owner), report number, CI and review verdicts to the owner, and set the ledger state to awaiting merge; the owner merges. When a reconcile is queued for this runner (`reconcile pending after PR <merged PR number>` in the pending question field), report the PR as waiting on a reconcile and not to be merged yet, set the state to `reconciling <merged PR number>` instead of awaiting merge, and send the Reconcile text. When the runner was sent a reconcile or is a fresh reconcile runner, also check the Reconcile: line, run `gh pr view <PR number> --json body` and check the body has a `Reconcile record` section, and compare the line's cross-story findings count with the reviewer child's transcript in the runner's subagent folder (the folder `missing_children` reads); the pins in CI detect deleted wording only, so these three checks are the launcher's detector; then send any queued Reconcile text and record the line in the runner's ledger entry for the scorecard. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; merge the pull request; copy the runner's numbers to the owner unchecked; |
| **blocked** | The first line reads "blocked" and the hand-back gives a reason. | Read the reason; when it is a story with no acceptance criteria, relay the gap to the owner with the recommendation to route the story through `user-story-generator` and keep running the other stories; relay any other blocker like an owner question; when the hand-back gives no options, send the reason and the runner's recommendation (or state that it gave none) and ask the owner what to do. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; draft acceptance criteria for the story; stop the other runners; |
| **cap reached** | The first line reads "cap reached" and the hand-back lists the open findings. | Relay the open findings and the options (the owner continues with more rounds, splits the todo, accepts with a follow-up, or drops it) with a recommendation; a fix-round cap override is owner-reserved. For a reconcile the fix-round count is a fresh count of 3 for that reconcile; the options are that the owner continues with more rounds, accepts with a follow-up, or drops the reconcile. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; allow a fourth fix round on the owner's silence; |
| **interim** | The first line reads "interim"; the work is still in progress. | Record the status in the ledger; take no other action, except resume the runner when the launcher holds a child-result notification for it or an owner answer to relay. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; relay it to the owner as a result; |
| **runner killed by a rate limit** | **Context:** A session rate limit ends running runners mid-flight, with no hand-back; the runner's branch and commits remain on disk. | After the limit resets, resume every killed runner with the validate-first text (see Resume texts), one validation before any continuation. **Forces:** A killed runner may have a child half-finished and uncommitted, and a continuation that assumes a clean tree can overwrite it. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; relaunch a runner whose branch exists (except the fresh reconcile runner of Close-out step 7 after a resume errors or no runner id is recorded); resume before the limit resets; |
| **child result delivered to the launcher while the runner is live** | **Context:** A notification carries a child's result and names a child of a runner that has not handed back, because a runner cannot wait on a background child or on a child resumed by message. | Resume the runner by message with the child-result text (see Resume texts), filling in the child's transcript path so it reads the result and continues. **Forces:** The result belongs to the runner's plan, and the launcher holds the only copy of the notification. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; act on the child's result itself; drop the notification; |
| **premature turn-end caused by a background child** | **Context:** A runner's turn ends right after it dispatched a background child, or after it resumed a child by message, and no kind line was sent. | Wait for the child's completion, then resume the runner with the child-result text (see Resume texts); do not relay it as a hand-back. **Forces:** The runner's later turns depend on a result it can no longer wait for, and a resume sent before the child finishes hands it half a result. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; relay the turn-end as a hand-back; resume the runner before the child finishes; |
| **hand-back missing a required line** | A line from the Required lines list below is absent, or the Discovery line has any value other than the two allowed. | Resume the runner with the missing-line text (see Resume texts), naming each missing line exactly. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; fill in the missing line itself; relay the hand-back to the owner as complete; |
| **owner reports a merge** | The owner says a pull request is merged. | Run the close-out sequence in the skill's Close-out section. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; close out before the owner's merge is confirmed on origin; skip the patch comparison that proves the merged commit holds the same changes as the pull request branch; |
| **runner reports an owner-reserved item as already decided** | **Context:** A hand-back states that a merge, a fix-round cap override or a scope change was decided or done, with no owner message in the launcher's session to match. | Verify the real state with gh pr view and git, relay the facts to the owner with a recommendation (keep, revert, or re-open the decision), and end the turn. **Forces:** A runner cannot see the owner's words and reads an earlier reply as consent, while a decision stated as done reads as settled. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; accept the decision as made; revert the change without the owner's answer; |

## Required lines in a runner hand-back

Check these before acting on any hand-back:

- The first line is a kind line naming one of the five kinds: owner question, PR ready, blocked, cap reached, interim.
- A Limitations: line is present.
- When the runner's plan file exists, a Discovery line whose value is exactly "Discovery: ran" or "Discovery: skipped: issue carries a Feature Specification"; any other value counts as a missing line.
- The reloaded skills are listed.
- When a pull request exists: the pull request number, the CI state and the review verdicts; when none exists, these three are absent.
- An owner question carries options and a recommendation.
- A cap reached hand-back states the open findings.
- When the runner was sent a reconcile (ledger state `reconciling`) or is a fresh reconcile runner, its PR ready hand-back carries a line of the form `Reconcile: merged PR <n>; files <list>; conflicts resolved <n>; cross-story findings <n>; fix rounds <n>; spec review <verdict>; CI <state>`, every count stated, zero written as 0. Its absence counts as a missing line.

## Hand-back size contract

**Context:** A hand-back enters the launcher's context in full, and the launcher cannot shorten it, so the runner's text is the only lever. Measured on two launcher sessions, hand-backs were 8.5% and 5.2% of the characters added to the launcher's main thread, with median hand-backs of 5,263 and 6,872 characters.
**Forces:** The launcher needs the decision lines to act. The detail (status per acceptance criterion, commit and hash lists, review narrative, slips, cleanup, follow-ups) already lives in the pull request body and the runner's plan file, so repeating it in the hand-back costs launcher context and adds no information.

This section is the one place the cap is stated.

- Cap: 3,000 characters for the whole final message, for every kind. The required lines above count inside the cap.
- Order: the first line is the kind line. The second line is one plain sentence naming what the owner or launcher must decide or confirm, or "no decision needed". The required lines follow.
- Detail: everything beyond the required lines goes in the pull request body, or in the runner's plan file when no pull request exists, never in a new report file. When anything was left out, the hand-back carries one line, `Detail: PR <n> body` or `Detail: <absolute plan file path>`; when nothing was left out it carries no Detail line.
- An owner question keeps its options and its recommendation inside the cap and never moves them to Detail.
- A hand-back over the cap is not a missing line. The launcher does not resume a runner to shorten it, because the resume produces a second hand-back. For a PR ready hand-back it relays only the decision sentence, the pull request number, the CI state and the review verdicts; every other kind is relayed as its row above says. It notes the overrun in the ledger.
- Before sending, the runner counts its final message with `printf '%s' "$MESSAGE" | wc -m` (the message held in a shell variable) and shortens it when the count is over the cap. A resend that the missing-line text asks for stays inside the cap too.
- The launcher reads the Detail target only when a decision needs it.

## Resume texts

Send these with the resume message, unchanged except for the placeholders.

- Validate-first text: "You were stopped by a session limit. Before dispatching anything, run git status and git log on the feature worktree and on every child worktree, and report what was in flight."
- Child-result text: "A child finished; its transcript is at <path>. Read it, continue, and dispatch every child with run_in_background false. Send every re-dispatched child (fix, re-check, or unreadable-verdict re-dispatch) as a fresh child, never a resumed one."
- Missing-line text: "Your hand-back lacks: <each missing line, named exactly>. Send the hand-back again with every number pasted from a command run in that turn."
- Reconcile text: "PR <merged PR number> merged as <merge commit> and touched files your branch also touches: <overlapping files>. Reconcile: fetch origin, rebase your branch onto origin/main, resolve each textual conflict keeping both stories' intent, and append a Reconcile record section to your PR body listing each resolved hunk and the reason (write 'no conflicts' when there are none). Then dispatch a fresh reviewer to read every overlapping file as it stands after the update against the acceptance criteria of both stories (the merged story is <merged story reference>) and to report each statement that now contradicts another statement and each acceptance criterion of either story that is no longer met, and fix each finding as a fix round of this reconcile. Push your own branch only, with --force-with-lease. Re-run CI and the spec review on the reconciled parts, then hand back PR ready with a Reconcile: line. When resolving needs dropping one story's intent, hand back owner question naming both intents and the hunk. Dispatch every child with run_in_background false."
