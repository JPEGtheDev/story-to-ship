# Hand-back routing table

This file is the launcher's routing table for a sprint. Each runner is a coordinator subagent (the story-coordinator template) that runs one story and hands back; the launcher is the session that started the runners, relays the owner's answers, resumes runners, and closes out merges. A child is a subagent a runner dispatched, never the runner itself. Read this file whenever a hand-back or a runner event arrives, before acting on it.

**Context:** A hand-back or event arrives while other runners are still working, and the quickest reply looks like answering the runner directly.
**Forces:** The launcher holds the owner's attention and the runners' branches, while a runner holds only its own story, so every reply that is not a lookup in this table risks a decision the owner never made. The owner-reserved decisions are exactly: merge, fix-round cap override, scope change. A scope change is a change to the work the story's acceptance criteria require, such as changing an acceptance criterion or adding behavior the story does not name; a file added for that work is not one.

Every cell in the Launcher must NOT column starts with the same four prohibitions, and each row adds its own after them.

| Hand-back or event | How the launcher recognizes it | Launcher response | Launcher must NOT |
|---|---|---|---|
| **owner question** | The first line of the hand-back reads "owner question"; it lists options and a recommendation. | Put the question to the owner as the card described below with the options and the runner's recommendation, record it as the pending question in the sprint ledger (the launcher plan file), and end the turn; when the owner answers, resume the runner with the answer. Add the question to the owner questions page (`OWNER_QUESTIONS.md`) as its card; the card carries the options and the recommendation, and chat gets only the one-line pointer. A hand-back of kind owner question, blocked or cap reached from the pilot keeps the pilot held; the answer to it is not a pass. The pilot line changes as the table in [PILOT.md](PILOT.md) says. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; answer the question from earlier rulings; resume the runner before the owner answers; |
| **PR ready** | The first line reads "PR ready"; the hand-back names the pull request number, the continuous integration (CI) state, and the review verdicts. | Run `gh pr view <n> --json isDraft` first; when isDraft is true, add no Ready to merge entry, do not set the ledger state to awaiting merge, do not report the pull request as ready, and then either (a) on the first PR ready hand-back for this pull request, send the Draft text (see Resume texts), or (b) on a second or later PR ready hand-back for it, send no Draft text and put it to the owner as a blocked card; when isDraft is false, continue: Run `sh skills/running-a-sprint/scripts/handback-check.sh -n <n> -w <runner worktree> -s <story number> [-b <base ref>] [-P <plan file>] [-m <old file> <new file> <text>]...` from the repository root (the relative path resolves only there), which runs the mechanical checks state, draft, mergeable, head, ci, branch, closing, footer, coauthor, ascii, inline and moved, printing one line per check as `OK <name>: <value>` or `FAIL <name>: <value>` and exiting 0 when every check is OK, 1 when any check fails or GitHub cannot be read, and 2 on a usage error; every FAIL line goes into what the launcher reports, and while any check is FAIL the launcher does not report the pull request as ready, does not add a Ready to merge entry and does not set the ledger state to awaiting merge. The -m option is for a pull request that moves text between files, with one -m per moved passage. Besides the check lines, the script prints `NOTE fetch: ran git fetch <remote> <branch>` when the branch check runs, one inline line for each file that a `lane: inline` clause names (or `OK inline: none` when none does), and one moved line for each -m (or `OK moved: none given` when no -m is given); a hash in the plan file's inline commits that does not resolve adds one FAIL inline line. When GitHub cannot be read, it prints only the ten FAIL lines for state, draft, mergeable, head, ci, branch, closing, footer, coauthor and ascii, with no NOTE, inline or moved line. The inline check reads every `<n> lines in <file>` clause that follows `lane: inline` in the plan file; clauses joined by "and" or "&" are read in the same chain, and any other word ends the chain. It adds up the n values of a file that is named more than once. The plan file is `plan.md` in the runner worktree by default; when that file is missing and -P is not given, the inline check prints `OK inline: none`, and when -P is given and the file is missing it prints `FAIL inline: plan file <name> not found`. So pass -P whenever the runner's plan file is not `<runner worktree>/plan.md`. The closing check counts a closing keyword followed by an issue URL, or with its keyword wrapped in asterisks or underscores, as a keyword, and skips lines inside fenced code blocks; -s takes digits only, and a non-numeric -s is a usage error (exit 2). Running the script is the launcher's own re-run of the state, draft, mergeable, head, ci, branch, closing, footer, coauthor, ascii and inline checks, and its lines are that re-run's result. The script does not check the review verdicts, the required lines, the `Record:` lines or the `Reconcile:` line; those stay hand-run, as this row says. When a script line disagrees with a hand-run result, re-run the script once; if they still disagree, report both results to the owner. Re-run `gh pr view <n> --json number,state,mergeable,headRefOid,statusCheckRollup,body` yourself for the pull request number, the CI state and the head (this is still the way to read them for the owner message), check the required lines, check that the PR state is OPEN, that mergeable is MERGEABLE, that headRefOid equals the runner worktree head (`git -C <runner worktree> rev-parse HEAD`), that the CI state on that head is green, and that the body has a closing keyword for the story and the footer line; run the inline-edit comparison when the runner made inline commits (a runner cannot read the inline-edit guard's ledger, the hook's record of inline edits, so compare the lane entries in its plan file, each todo's record of its route written as lane: dispatch or lane: inline with a line count and a file name, with git diff --numstat over the runner's inline commits, where a replaced line counts 2, and report any mismatch to the owner), a `Record:` line from a runner still on the old text is ignored: the launcher does not open its path, does not count it as an extra line and does not resume the runner for it, report number, CI and review verdicts to the owner, and set the ledger state to awaiting merge; the owner merges. When a reconcile is queued for this runner (`reconcile pending after PR <merged PR number>` in the pending question field), report the PR as waiting on a reconcile and not to be merged yet; when its PR becomes next to merge, set the state to `reconciling <merged PR number>` instead of awaiting merge and send the Reconcile text, and until then do not set awaiting merge. When the runner was sent a reconcile or is a fresh reconcile runner, also check the Reconcile: line, run `gh pr view <PR number> --json body` and check the body has a `Reconcile record` section, and compare the line's cross-story findings count with the reviewer child's transcript in the runner's subagent folder (the folder `missing_children` reads); the pins in CI detect deleted wording only, so these three checks are the launcher's detector; then send any queued Reconcile text and record the line in the runner's ledger entry for the scorecard. Add a Ready to merge entry for the pull request to the owner questions page (`OWNER_QUESTIONS.md`), not a card: add it only when no owner decision about the PR is open (a PR with one keeps a card for that decision only), and only when no reconcile is queued for this runner, or once the Reconcile checks above have passed when a reconcile was queued. When the runner is the pilot (the ledger's pilot line names this runner's story and its result is held, failed, passed or released), the pilot line changes as the table in [PILOT.md](PILOT.md) says; a PR ready hand-back of the pilot that fails a launcher check puts the failure on the owner questions page as a card and does not resume the runner. A PR ready hand-back of the pilot that lacks a required line alone keeps the missing-line row's outcome. When a PR ready hand-back that is not a draft lacks a required line and fails a launcher check, the failed check governs: the launcher adds the card, lists the missing lines on it, and does not resume the runner. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; merge the pull request; copy the runner's numbers to the owner unchecked; |
| **blocked** | The first line reads "blocked" and the hand-back gives a reason. | Read the reason; when it is a story with no acceptance criteria, put the gap to the owner as the card described below with the recommendation to route the story through `user-story-generator` and keep running the other stories; treat any other blocker like an owner question; when the hand-back gives no options, put the reason and the runner's recommendation (or state that it gave none) on the card and ask the owner what to do. Add the question to the owner questions page (`OWNER_QUESTIONS.md`) as its card; the card carries the options and the recommendation, and chat gets only the one-line pointer. A hand-back of kind owner question, blocked or cap reached from the pilot keeps the pilot held; the answer to it is not a pass. The pilot line changes as the table in [PILOT.md](PILOT.md) says. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; draft acceptance criteria for the story; stop the other runners; |
| **cap reached** | The first line reads "cap reached" and the hand-back lists the open findings. | Put the open findings and the options (the owner continues with more rounds, splits the todo, accepts with a follow-up, or drops it) with a recommendation, as the card described below; a fix-round cap override is owner-reserved. For a reconcile the fix-round count is a fresh count of 3 for that reconcile; the options are that the owner continues with more rounds, accepts with a follow-up, or drops the reconcile. Add the question to the owner questions page (`OWNER_QUESTIONS.md`) as its card; the card carries the options and the recommendation, and chat gets only the one-line pointer. A hand-back of kind owner question, blocked or cap reached from the pilot keeps the pilot held; the answer to it is not a pass. The pilot line changes as the table in [PILOT.md](PILOT.md) says (an owner drop of the pilot writes released). | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; allow a fourth fix round on the owner's silence; |
| **interim** | The first line reads "interim"; the work is still in progress. | Record the status in the ledger; take no other action, except resume the runner when the launcher holds a child-result notification for it or an owner answer to relay. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; relay it to the owner as a result; |
| **runner killed by a rate limit** | **Context:** A session rate limit ends running runners mid-flight, with no hand-back; the runner's branch and commits remain on disk. | After the limit resets, resume every killed runner with the validate-first text (see Resume texts), one validation before any continuation. **Forces:** A killed runner may have a child half-finished and uncommitted, and a continuation that assumes a clean tree can overwrite it. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; relaunch a runner whose branch exists (except the fresh reconcile runner of Close-out step 7 after a resume errors or no runner id is recorded); resume before the limit resets; |
| **child result delivered to the launcher while the runner is live** | **Context:** A notification carries a child's result and names a child of a runner that has not handed back, because a runner cannot wait on a background child or on a child resumed by message. | Resume the runner by message with the child-result text (see Resume texts), filling in the child's transcript path so it reads the result and continues. **Forces:** The result belongs to the runner's plan, and the launcher holds the only copy of the notification. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; act on the child's result itself; drop the notification; |
| **premature turn-end caused by a background child** | **Context:** A runner's turn ends right after it dispatched a background child, or after it resumed a child by message, and no kind line was sent. | Wait for the child's completion, then resume the runner with the child-result text (see Resume texts); do not relay it as a hand-back. **Forces:** The runner's later turns depend on a result it can no longer wait for, and a resume sent before the child finishes hands it half a result. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; relay the turn-end as a hand-back; resume the runner before the child finishes; |
| **hand-back missing a required line** | A line from the Required lines list below is absent, or the Discovery line has any value other than the two allowed. | Resume the runner with the missing-line text (see Resume texts), naming each missing line exactly, unless the hand-back is a PR ready hand-back that is not a draft and fails a launcher check; then the failed check governs (see the PR ready row) and the runner is not resumed. When the runner is the pilot (the ledger's pilot line names this runner's story and its result is held, failed, passed or released), the pilot line changes as the table in [PILOT.md](PILOT.md) says, and a card naming the missing lines goes on the owner questions page for every kind; the resume with the missing-line text still goes out for every kind except the failed-check case above. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; fill in the missing line itself; relay the hand-back to the owner as complete; |
| **owner reports a merge** | The owner says a pull request is merged, in chat or as a comment on the page. | Run the close-out sequence in the skill's Close-out section; after it has run, remove the PR's Ready to merge entry from the owner questions page, republish the page, re-read it and send the owner one chat line. The two scripts that run its steps 1-5 and the reads of step 6 are described in `references/CLOSE_OUT.md`. A merge of the pilot story while its pilot line reads failed writes released, as the table in [PILOT.md](PILOT.md) says. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; close out before the owner's merge is confirmed on origin; skip the patch comparison that proves the merged commit holds the same changes as the pull request branch; |
| **runner reports an owner-reserved item as already decided** | **Context:** A hand-back states that a merge, a fix-round cap override or a scope change was decided or done, with no owner message in the launcher's session to match. | Verify the real state with gh pr view and git, relay the facts to the owner with a recommendation (keep, revert, or re-open the decision), and end the turn. **Forces:** A runner cannot see the owner's words and reads an earlier reply as consent, while a decision stated as done reads as settled. | NOT: decide for the owner; resume a child by message; coach mid-run; answer a child itself; accept the decision as made; revert the change without the owner's answer; |

## Required lines in a runner hand-back

Check these before acting on any hand-back:

- The first line is a kind line naming one of the five kinds: owner question, PR ready, blocked, cap reached, interim.
- A Limitations: line is present.
- When the runner's plan file exists, a Discovery line whose value is exactly "Discovery: ran" or "Discovery: skipped: issue carries a Feature Specification"; any other value counts as a missing line. When no plan file exists (a blocked hand-back for an issue with no acceptance criteria, or a fresh reconcile runner), the line is absent and its absence is not a missing line.
- The reloaded skills are listed.
- When a pull request exists: the pull request number, the CI state and the review verdicts; when none exists, these three are absent.
- An owner question carries options and a recommendation.
- A cap reached hand-back states the open findings.
- When the runner was sent a reconcile (ledger state `reconciling`) or is a fresh reconcile runner, its PR ready hand-back carries a line of the form `Reconcile: merged PR <n>; files <list>; conflicts resolved <n>; cross-story findings <n>; fix rounds <n>; spec review <verdict>; CI <state>`, every count stated, zero written as 0. Its absence counts as a missing line.

## Hand-back size contract

**Context:** A hand-back enters the launcher's context in full, and the launcher cannot shorten it, so the runner's text is the only lever. Measured on two launcher sessions, hand-backs were 8.5% and 5.2% of the characters added to the launcher's main thread, with median hand-backs of 5,263 and 6,872 characters.
**Forces:** The launcher needs the decision lines to act. The detail (status per acceptance criterion, commit and hash lists, review narrative, slips, cleanup, follow-ups) already lives in the pull request body and the runner's plan file, so repeating it in the hand-back costs launcher context and adds no information.

This section is the one place the cap is stated.

- Cap: 3,000 characters for the whole final message, for every kind. The required lines above count inside the cap.
- Order: the first line is the kind line. The second line is one plain sentence naming what the owner or launcher must decide or confirm, or "no decision needed". The required lines follow.
- Detail: everything beyond the required lines goes in the pull request body, or in the runner's plan file when no pull request exists, never in a new report file. When anything was left out, the hand-back carries one line, `Detail: PR <n> body` or `Detail: <absolute plan file path>`; when nothing was left out it carries no Detail line.
- An owner question keeps its options and its recommendation inside the cap and never moves them to Detail.
- A hand-back over the cap is not a missing line. The launcher does not resume a runner to shorten it, because the resume produces a second hand-back. For a PR ready hand-back it relays only the decision sentence, the pull request number, the CI state and the review verdicts; every other kind is handled as its row above says. It notes the overrun in the ledger. Being over the cap does not fail the pilot check.
- Before sending, the runner counts its final message with `printf '%s' "$MESSAGE" | wc -m` (the message held in a shell variable) and shortens it when the count is over the cap. A resend that the missing-line text asks for stays inside the cap too.
- The launcher reads the Detail target only when a decision needs it.

## Resume texts

Send these with the resume message, unchanged except for the placeholders.

- Validate-first text: "You were stopped by a session limit. Before dispatching anything, run git status and git log on the feature worktree and on every child worktree, and report what was in flight."
- Child-result text: "A child finished; its transcript is at <path>. Read it, continue, and dispatch every child with run_in_background false. Send every re-dispatched child (fix, re-check, or unreadable-verdict re-dispatch) as a fresh child, never a resumed one."
- Missing-line text: "Your hand-back lacks: <each missing line, named exactly>. Send the hand-back again with every number pasted from a command run in that turn."
- Draft text: "Your pull request <n> is still a draft. When CI is green on its current head and the whole-branch review has passed on that head, run gh pr ready <n>, check that gh pr view <n> --json isDraft prints false, then send the PR ready hand-back again; otherwise wait for green CI and finish the reviews first."
- Reconcile text: "PR <merged PR number> merged as <merge commit> and touched files your branch also touches: <overlapping files>. Reconcile: fetch origin, rebase your branch onto origin/main, resolve each textual conflict keeping both stories' intent, and append a Reconcile record section to your PR body listing each resolved hunk and the reason (write 'no conflicts' when there are none). Then dispatch a fresh reviewer to read every overlapping file as it stands after the update against the acceptance criteria of both stories (the merged story is <merged story reference>), to read each rule section that both PRs edited for rules that contradict each other, reporting each such contradiction and not only the conflicting hunks, and to report each statement that now contradicts another statement and each acceptance criterion of either story that is no longer met, and fix each finding as a fix round of this reconcile. Push your own branch only, with --force-with-lease. Re-run CI and the spec review on the reconciled parts, then hand back PR ready with a Reconcile: line. When resolving needs dropping one story's intent, hand back owner question naming both intents and the hunk. If your pull request is ready, run gh pr ready <n> --undo before you start, and mark it ready again only after CI and the reconcile review have passed on the updated head. Dispatch every child with run_in_background false."
