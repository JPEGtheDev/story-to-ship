# Reconcile (Close-out step 7)

7. Reconcile the PR next to merge against the merged change. That PR is the first entry on the Ready to merge list once the merged PR's entry is removed (the list is in the recommended merge order; OWNER_QUESTIONS.md names it); the other open sprint PRs wait and are reconciled when they become next. Take the merged change's files from `git -C R diff --name-only S^ S`. List that PR's files with `gh pr diff <PR number> --name-only` (do not use `--json files`; it is capped at 100 files) and intersect the two lists. An empty intersection means no reconcile is sent for that PR. When `gh pr diff` fails for that PR, compare its Files list (the Files to Create/Modify list of its story) with the merged change's files instead; that is the fallback. When neither the diff nor a Files list is available, send the Reconcile text and let the runner read the merged change's files against its own diff. A reconcile reviews only the resolved conflict hunks on the conflicting files and the changed files of its fix rounds, plus CI; a clean rebase with no conflict and no fix round needs green CI only, with no reviewer.
   - For a non-empty intersection, resume that PR's runner with the Reconcile text from `references/HANDBACK_ROUTING.md` (Resume texts), fill its placeholders, and set the ledger state to `reconciling <merged PR number>`.
   - A runner still working whose PR is not next to merge has `reconcile pending after PR <merged PR number>` added to its pending question field, and gets the Reconcile text when its PR becomes next to merge, not when it hands back PR ready; a hand-back of owner question, blocked or cap reached follows the next bullet. The launcher's one-line message to the owner says the PR is waiting on a reconcile and is not to be merged before the reconcile finishes.
   - A runner held on an owner question, blocked or cap reached has `reconcile pending after PR <merged PR number>` added to its pending question field, after the owner's open question and without replacing it, until the owner has answered and its PR becomes next to merge. The launcher's one-line message to the owner says the PR is waiting on a reconcile.
   - A killed runner is resumed, after the limit resets, with the validate-first text from `references/HANDBACK_ROUTING.md` and then treated as a working runner (`reconcile pending after PR <merged PR number>`).
   - A runner that cannot be resumed (the resume errors, or no runner id is recorded) is replaced by a fresh runner launched like any other: the four inputs and the scope "reconcile PR <n> after PR <m> merged, branch <branch>"; it counts toward capacity. The fresh runner fetches both stories, both diffs and the PR body itself, works in a worktree made from `origin/<branch>`, and opens no new PR. A reconcile replacement is exempt from the limit and the dependency rule, because it takes over a story that already holds its slot and branch. The launcher adds the merge commit and the overlapping files to the scope. The ledger entry gets the new runner id, the fresh runner's worktree prefix, and its local branch `reconcile-<prefix>`.
   - A reconcile in progress finishes before the next one is sent to the same runner: a second merge adds another `reconcile pending after PR <merged PR number>` entry to the pending question field, and the queued Reconcile text goes out when the running reconcile's PR ready hand-back is verified. Whenever a Reconcile text is sent, set the state to `reconciling <merged PR number>`. When a PR itself merges, drop its reconcile entries from the ledger.
   - Find open PRs outside the ledger with `gh pr list --state open --json number`. A PR with no ledger entry is not reconciled; when `gh pr diff <n> --name-only` shows an overlap, tell the owner in one line "PR <n> overlaps the merged change but is not a sprint PR".
   - The runner answers with a PR ready hand-back that carries a `Reconcile:` line. Verify it like any other PR ready (`references/HANDBACK_ROUTING.md`), then tell the owner in one line that the PR head changed and needs a fresh look.
   - There is no cap on open PRs. A PR that is not next to merge waits with its `reconcile pending after PR <merged PR number>` entry, and the number of open PRs is not a reason to skip the reconcile of the PR that is next.
