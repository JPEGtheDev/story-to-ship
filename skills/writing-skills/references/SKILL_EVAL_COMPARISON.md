# Old-Versus-New Eval Comparison

Use this procedure before shipping an edit that shortens or rewords a skill. It measures the change; it does not shorten anything.

## a. When It Applies

1. Run this procedure before shipping any edit that shortens or rewords a skill's SKILL.md or references/ text. Step d.1 compares the commit before the edit with the edited tree, so the comparison runs after the edit and before shipping.
2. Ship the changed skill only when no kept case ends in a confirmed LOSS. A LOSS at a stage is not a verdict: step d.7 confirms it with a batch of 30 fresh runs, and a confirmed LOSS blocks the change. There is no tolerance for a confirmed LOSS. A model default case or a case with no verdict has no pass or fail result from this procedure; it gates the ship only through the pre-ship check (section i, item 6). A weak targeted case carries no stage verdict and is gated by its focused cycles (step d.9).
3. Skip rule. A case whose 30-run reference labels it model default (section i, item 2) is kept in the model-default folder, written `<model-default-dir>` in this file: the path of that folder, which the operator passes with `--eval-dir`. `<default-dir>` means the default eval folder, the folder run with no `--eval-dir`. The case carries `bin: model default` and a `skip:` block in its `case.yaml`. The `skip:` block holds the fields `model`, `claude_code_version`, `with_skill`, `without_skill` and `source`. A case in the default folder (`<default-dir>`) carries neither marker. Everyday runs read `<default-dir>` with no tag filter and never read `<model-default-dir>`. A `--tag` that selects no case makes `claude plugin eval` exit 1 with "No eval cases found"; that exit means a missing tag on the case files, not a pass. Two kinds of run read `<model-default-dir>`, and no others: the new-model step (section j, item 13), and the default-ablation run of a model default case (section i, item 8), made once when the case is first classified and again when its grader changes.

## b. Consent and Cost

1. Every eval run uses model usage. Get the owner's consent for each run before starting it.
2. Pass a ceiling on every run: `--max-cost-usd <ceiling>`.
3. Consent for one run does not cover a rerun or a changed command. Ask again.
4. A comparison's cost is the reference run, the stage runs and the fresh batch, each counted as its own run with its own ceiling. A kept set that one `--case` glob cannot select is split into one comparison per glob, and each comparison carries that cost.
5. If consent is withheld, no run happens. Do not ship the change on the strength of this procedure.
6. `--scaffold` runs each case's `scaffold.sh` as bash on the machine as the user running the command. Run evals only on code you have read, including every `scaffold.sh` in both checkouts.

## c. Cases and Checkouts

1. Cases live in the default folder (`<default-dir>`) or in the model-default folder (`<model-default-dir>`), by label: a case with `bin: model default` and a `skip:` block lives in `<model-default-dir>`; every other case lives in `<default-dir>`. Each case folder holds `prompt.md`, `graders/*.md`, `case.yaml` and `scaffold.sh`. `scaffold.sh` builds the small test repository the case runs in. Each case has one rule.
2. Both checkouts must hold identical `<default-dir>` directories. Run `diff -r -x results <old-path>/<default-dir> <new-path>/<default-dir>`. Continue only when it prints nothing and exits 0.

## d. Steps

1. Make the old checkout: `git worktree add <old-path> <base-commit>`, where `<base-commit>` is the commit before the edit. Keep the edited tree as the new checkout at `<new-path>`.
2. Run the old checkout once for the reference, 30 runs per case. Reuse a cached reference result while its cache key is unchanged (section i, item 9); run it again only when the key changes.
   `claude plugin eval <old-path> --runs 30 --model <model> --judge-model <judge-model> --ablation none --scaffold --allow-tools Edit --no-publish --max-cost-usd <ceiling> --json <old.json>`
   Add `--case <glob>` to this command when a case subset applies (step d.3). A first comparison with no earlier classification omits it, so every case in the default eval folder runs.
3. Run the same command on `<new-path>` with `--json <new.json>`, with the same case selection and `--runs <new runs>`: 5 new runs for stage 5, 10 new runs for stage 15 and 15 new runs for stage 30 (the stage rules are in step d.6). The candidate run file is cumulative: for each case it keeps the runs of every earlier stage and adds the new runs, in the same JSON shape, so `cand=` holds all runs taken so far for that case (5, then 15, then 30). The cumulative file is seeded only by the final 5-of-5 file of each case (step d.9). The run for each stage is one candidate file that holds only the cases that reached that stage (the cases still open at stage 5, 15 or 30); a case that ended at an earlier stage is dropped from the later file. Merge each new run file into the cumulative file by appending its records for each case to that case's records. Keep the same `--model`, `--judge-model`, `--scaffold`, and `--allow-tools Edit` on both. `claude plugin eval --help` lists `--case <glob>`, which filters cases by name glob, and `--eval-dir <dir>`, which names the eval folder below the plugin; the default eval folder is used when `--eval-dir` is omitted. A kept set that one glob cannot select needs one comparison per glob, each with its own consent (section b, item 3). A first comparison with no earlier classification runs every case, with no `--case`; the focused-first rule of step d.9 applies to the runs after a text, grader or case-prompt change that follows an earlier classification. In every later comparison, a case keeps its stage runs unless the last grouping output (section i, item 5) printed the label model default or weak for it. The run count is at most 30 runs per kept case (section h, item 1). A case labeled model default runs only as section i, item 8 states, and has no pass or fail result (section i, item 6). A case labeled weak gets the focused cycles of step d.9 when targeted, and no stage runs.
4. Join and print the per-case scores and the difference. Here new.json is the cumulative candidate file of step d.3. With one comparison per glob, join each glob's old and new json files separately and read each glob's verdict on its own; no step joins results across globs. The join reads every case in old.json. A case missing from new.json gets the row `error, no verdict` for that case, and the comparison has no verdict:
   `jq -n --slurpfile o <old.json> --slurpfile n <new.json> '[ $o[0].cases[] as $a | ([ $n[0].cases[] | select(.name==$a.name) ] | .[0]) as $b | if $b == null then {case:$a.name, verdict:"error, no verdict"} else {case:$a.name, old:$a.aggregates.score, new:$b.aggregates.score, diff:($b.aggregates.score-$a.aggregates.score)} end ]'`
5. Run the verdict script on the reference file and the cumulative candidate file (step d.3): `python3 skills/writing-skills/scripts/eval_verdict.py --stage <5|15|30> ref=<old.json> cand=<new.json> [fresh=<fresh.json>]`, once per stage with that stage's candidate file (step d.3). The script checks every case in the file against the one `--stage`, so a case that stopped at a different stage must not be in that file. It prints one line per case: the name, the one-sided Fisher p and the stage verdict. A run with a non-null error is dropped before counting, the dropped count is printed (`<case>: dropped N` for the candidate, `<case>: dropped N (reference)` or `<case>: dropped N (fresh)` for the other files), and the run is rerun. A reference, candidate or fresh file that keeps zero runs for a case, or a candidate with more runs than the stage, is a refusal with exit 2, and the message goes to standard error. The script uses only the Python standard library. A negative `diff` in step d.4 is a score table, not a verdict; the verdict comes from this script.
6. Stage rules. The candidate's runs are cumulative: the 5 runs of stage 5 count toward stage 15, and the 15 runs of stage 15 count toward stage 30. No case gets more than 30 runs. The reference is the cached 30-run result. p is the exact probability that the candidate has at least as many failures as observed, given the pooled pass and fail totals of both arms.
   - Stage 5: NEXT when the candidate passes 5 of 5; else LOSS when p is at most 0.01; else EDIT, and the case goes back to editing.
   - Stage 15: LOSS when p is at most 0.05; else HOLD when the candidate passes 15 of 15 or its rate is at or above the reference rate; else NEXT. 13 of 15 and 14 of 15 against a 30 of 30 reference are NEXT.
   - Stage 30: LOSS when p is at most 0.05, else HOLD.
   Examples with a 30 of 30 reference: candidate 2 of 5 gives p 0.001528, LOSS. Candidate 3 of 5 gives p 0.016807, EDIT. Candidate 12 of 15 gives p 0.032065, LOSS. Candidate 13 of 15 gives p 0.106, NEXT. Candidate 15 of 15 gives HOLD. With a 27 of 30 reference, candidate 14 of 15 gives HOLD and candidate 13 of 15 gives NEXT.
   A stage cut short by its spend cap, or one with fewer runs than the stage count after dropped errors, gets no verdict (the script exits 2 and says rerun). Rerun the stage with the owner's consent and a ceiling; the partial result is not counted.
7. A LOSS at any stage is confirmed by a separate batch of 30 fresh runs of the candidate, recorded in full. Pass the fresh file as `fresh=<fresh.json>`; the script prints `confirm=LOSS` when the fresh batch alone shows p at most 0.05 against the reference, else `confirm=HOLD`. The fresh batch must hold exactly 30 kept runs for each case that has a LOSS, and a LOSS case missing from the fresh file is exit 2; the script refuses both, so rerun the batch. The `confirm=` value decides the LOSS. A LOSS that the fresh runs do not confirm is HOLD, and the skill wording stays in place. A confirmed LOSS blocks the change and puts one standalone line back into the skill. The confirmation batch needs the owner's consent and a ceiling.
8. NEXT at stage 5 sends the case to its 15-run stage, and EDIT at stage 5 sends it back to editing. NEXT at stage 15 sends the case to its 30-run stage. HOLD at stage 15 or 30 ends the case with no loss. If every kept case ends in HOLD, the change may ship. Record each stage result and each fresh batch with the comparison.
9. Focused first. The first paid run after a text, grader or case-prompt change that follows an earlier classification is 5 runs on the targeted cases only; a first comparison with no earlier classification runs every case (step d.3). The plan names the targeted cases with a `--case` glob. A targeted case under 5 of 5 gets the stage-5 verdict, which is LOSS when p is at most 0.01 and EDIT otherwise; a case with EDIT goes back to editing. A dropped errored run does not count toward the 5; its rerun is an extra run. Each focused cycle writes a new candidate file. Other targeted cases keep their own cycles. The focused-cycle cap is 5 cycles per case. A case at the cap without 5 of 5 goes to an owner question and blocks shipping. A targeted case labeled weak (section i, item 5) runs focused 5-run cycles like any other targeted case under the same 5-cycle cap, a cycle passes only when it reaches 5 of 5, and a cycle under 5 of 5 goes back to editing, as an EDIT case does, and the case repeats until a cycle reaches 5 of 5 or the cap, because a weak case carries no stage verdict and is not judged by the stage-5 LOSS or EDIT rule; at the cap without 5 of 5 the case goes to an owner question and blocks shipping. A weak case runs no 15-run or 30-run stage. A targeted case that is not weak and reaches 5 of 5 may run its 15-run and 30-run stages, and the 30 fresh confirmation runs of a loss, while other targeted cases are still in focused cycles. Those stages run on targeted cases only. The cumulative 15-run file is seeded only by the final 5-of-5 file of each case.
10. Whole suite. After every targeted case that has stage runs has ended in HOLD and every weak targeted case has reached 5 of 5 in its focused cycles (a case still at its 15-run or 30-run stage, or with a confirmed LOSS, has not ended in HOLD; a weak case still in focused cycles has not ended, and a weak case at the cycle cap goes to an owner question, which stops the run; a case labeled model default has no pass or fail result and does not count), run the whole suite once with 30 runs per case. Two separate forms apply. The `eval_verdict.py --suite` form compares a reference file with a candidate file and selects nothing. The `claude plugin eval <path>` form runs the cases of one eval folder: the whole-suite run covers the default folder only (`<default-dir>`, no tag filter) and does not read `<model-default-dir>` (section a, item 3). Every case is compared with its saved reference:
   `python3 skills/writing-skills/scripts/eval_verdict.py --suite ref=<old.json> cand=<new.json>`
   Per case the output line is `<name>: ref=<p>/<n> cand=<p>/<n> BELOW` (BELOW means the candidate's pass rate is below the reference's pass rate) or `<name>: ref=<p>/<n> cand=<p>/<n> OK`, and the summary line `below reference: <count>` prints last. Report every case printed BELOW before any ship decision. The run exits 0 with BELOW lines. It exits 2 for a case missing on either side, for a case whose candidate has other than 30 kept runs, and for a case whose reference file keeps no runs. A `--suite` run is a paid run: it needs the owner's consent and its own `--max-cost-usd` ceiling. The reference and the candidate must hold the same cases. A reference file that holds a case now in `<model-default-dir>` still holds it, so drop those cases from the reference file first, with `<skip-names>` the JSON list of the model-default case names:
   `jq --argjson skip '<skip-names>' '.cases |= map(select(.name as $n | ($skip | index($n)) == null))' <old.json> > <old-default.json>`
   Then pass `ref=<old-default.json>`. The output form of `eval_verdict.py` does not change.
11. A grader or case prompt changed after its saved reference was recorded gets numbers only from runs made after the change. Record the reference again, or take it from old-checkout runs made after the change.

## e. Why These Flags

1. `--ablation none`: the default compares the plugin against no plugin and makes `tool_used: Skill` graders display-only. A comparison between two plugin versions needs those graders to count. The flag also halves the spend.
2. `--no-publish`: keeps the HTML report local.
3. `--scaffold --allow-tools Edit`: `--scaffold` is an opt-in that runs each case's `scaffold.sh` so the case has its test repository (without it the case runs in an empty folder), and the test repository's answers differ from the plugin's own files, so a session that reads the plugin folder instead gets the wrong answer; `--allow-tools Edit` is an operator grant that lets the `session-bootstrap-first` case edit its README; both are part of the owner's consent for the run.
4. Model tiers: run the sessions at the Economy tier and the judge at the Standard tier (`--model` and `--judge-model`), the same on both checkouts. The tiers are defined in the Model Selection section of the subagent-driven-development skill; this note names tiers only, so the procedure does not change when a model name does.

## f. Failure Outcomes

1. A run that hits the ceiling exits 2 with partial results and gives no verdict. The partial result is not counted. Either raise the ceiling with the owner's consent and rerun the stage, or do not ship.
2. A case without a grader, a bad grader field, or a bad checkout path fails when the suite loads. No verdict exists.
3. A missing json file means no verdict.
4. Results are written under the `results/` directory of each eval folder (`<default-dir>` and `<model-default-dir>`) in each checkout. Those directories are gitignored.

## g. Token Cost

1. Record the skill's on-invoke cost before and after the change, next to the eval comparison.
2. Run `claude --plugin-dir <old-path> plugin details story-to-ship`.
3. Run `claude --plugin-dir <new-path> plugin details story-to-ship`.
4. Confirm the output line `Source: story-to-ship@inline` in each run. It shows the command read the checkout, not the installed copy.
5. Find the skill's row under "Per-component" and read the `on-invoke` column. The readout rounds values; record the value as printed.
6. Use this number, not the chars/4 estimate in `SIZE_AND_COMPRESSION.md`, as the recorded saving.
7. Record one line per change in this format:
   `<skill>: <old on-invoke> -> <new on-invoke>; eval: <n> cases, no drop`

## h. Limits

1. Scores come from model runs. Use at most 30 runs per kept case, in the stages of step d.6. The chance that a stage returns LOSS for a candidate whose true pass rate is 70 percent, against a 30 of 30 reference, is 0.163 at 5 runs, 0.873 at 15 runs and 0.970 at 30 runs. Each figure is the exact binomial sum, over the pass counts the stage calls LOSS, of the chance of that count; it is for that stage alone. Only the 30-run stage is sized to catch a 30-point loss; stage 5 catches only a near-total loss, and stage 15 catches a 30-point loss 87 times in 100. At 0 passes in 15 runs, the one-sided 95 percent bound on the pass rate is 0.181; at 30 runs it is 0.095. The bound applies at 0 passes or n passes out of n runs and states no detection power. At n passes out of n runs, the same value bounds the fail rate (section i, item 3).
2. A case that scores the same with and without the plugin (the completion-claim case is one) does not prove the skill text matters.
3. A passing comparison shows no measured drop. It does not show the text is unneeded. A model default case carries no verdict and gates a ship through the pre-ship check (section i, item 6). A weak targeted case carries no stage verdict and is gated by its focused cycles (step d.9).
4. The join reads cases[].aggregates.score; check that field exists in the first --ablation none output before trusting the table.
5. Coverage: each eval case exercises one rule: `session-bootstrap-first` the first-tool-is-session-bootstrap rule, `completion-claim-evidence` the rule that a completion claim carries its evidence, `dispatch-passes-model` the rule that an Agent dispatch passes a model, `hold-rule-names-state` the rule that a hold rule names its state value, where it is stored, who clears it and what a repeat does, `shared-decisions-contradiction` the rule that a runner reports contradicting shared decisions instead of dispatching them, `using-git-worktrees-iron-law` the rule that a subagent dispatch names a worktree under `.worktrees/` and an `agent/<name>` branch (the commit target and the rule against main are not graded), `using-git-worktrees-before-proceeding-path` the rule that a subagent prompt names the worktree's absolute path, `using-git-worktrees-create-verify-toplevel` the rule that a run queries `git rev-parse --show-toplevel` before dispatch (one grader needs a `--show-toplevel` query in any Bash call; the other needs one Bash command that names a `.worktrees/` path and `--show-toplevel`, run before the first Agent call; neither compares the result with the worktree path), `using-git-worktrees-red-flag-relative-path` the rule against a `git worktree add ../` path, `using-git-worktrees-red-flag-main-checkout` the rule against switching branches (a `git checkout` or `git switch` to another branch, `gh pr checkout`, or a branch made in place is flagged in any directory; returning to `main` is allowed, and the run must also create the branch with `git worktree add`), `using-git-worktrees-red-flag-merge-before-diff` the rule that a worktree branch's diff is read before it is merged, `using-git-worktrees-base-check-before-add` the rule that a run checks the base with a `git rev-list` command (`rev-list --left-right`, or `rev-list --count` naming origin/main; a pass does not prove that origin/main was compared, the order against `git worktree add` is not graded, and a quoted origin/main in the `--count` form is missed), `using-git-worktrees-cleanup-after-merge` the rule that a worktree is removed after its branch is merged, `using-git-worktrees-git-c-after-cd` the rule that git commands read the checkout with `git -C` after a `cd` (a bare `git` in a separate call after a `cd`, or split from it by a newline, is not graded; the run must also read the checkout with `git -C`), `using-git-worktrees-list-count-check` the rule that the toplevel is read with `git rev-parse --show-toplevel`, not by counting `git worktree list` lines (the comparison with the expected path is not graded), `using-git-worktrees-list-active-worktrees` the rule that the active worktrees are listed with `git worktree list` (the order against `git worktree add` is not graded), `using-git-worktrees-gitignore-before-add` the rule that `.gitignore` is written before a worktree is created (a Bash `>`, `>>`, `tee` or `sed -i` write to `.gitignore`, in a command that names `.worktrees` and runs before the first `git worktree add`; a read or `git check-ignore` does not count), `using-git-worktrees-promised-not-main` and `using-git-worktrees-simple-task-excuse` the rule that a run creates the worktree before its first Agent dispatch (the dispatch must also name a `.worktrees/` path), `using-git-worktrees-unreviewed-landed-commit` the rule that a landed commit is read with `git show` before any revert, reset, checkout or branch delete (the read is graded by command form, not by what the run decides). A skill with no case gets no result from this procedure: a passing comparison says nothing about it.
6. What each case does and does not show: `completion-claim-evidence` scored the same with and without the plugin in its recorded run, so it does not show that the plugin text matters. In the recorded run of `dispatch-passes-model`, the session without the plugin made no Agent call (the grader reported "Agent called 0x"), so that case's score does not measure whether the model was passed. `session-bootstrap-first` tests the hook text injected at session start and before the first prompt, not the skill body.
7. A session can read the plugin folder: a session may open the plugin's own files instead of the test repository. The scaffolded repositories hold answers that differ from the plugin's files, so such a session scores wrong, but a case that does not check the answer (the dispatch and bootstrap cases) cannot catch it.

## i. Pair Bounds, Grouping and Labels

1. Group the run files with `python3 skills/writing-skills/scripts/eval_grouping.py label=path [label=path ...]`, one `label=path` item per run file. The caller chooses the labels. Pooling works by repeating a label: run files given the same label are concatenated under that label, in argument order. A label for a no-skill run starts with the prefix `no-skill`. Build that run file from a default-ablation run (item 8): the script reads only `cases[].arms.with`, so the records of the no-plugin arm of that run must sit under `arms.with` in the file the script reads. The arm's key name is not shown in this repository; read it from a default-ablation output before you copy the records.
2. The grouping gives each case one label from its pass rate under each label. Separating: the current skill passes more often than no-skill. Model default: no-skill passes at least as often as the current skill (a greater-or-equal test, not equality); the skill text for that rule is deleted, and the case is labeled `bin: model default` with a skip block (section a, item 3). Its runs are set by section i, item 8. Weak: the current skill passes under 90 percent of runs (26 of 30 is weak, 27 of 30 is not); a case that is both weak and model default takes weak, and weak takes precedence over separating as well as over model default. A kept case is a separating case. Model default and weak cases are not kept cases and get no stage verdict. A case is unclassified, and the script prints the instruction to run no-skill first, in three situations: the rates are equal under every label and no label starts with no-skill; the rates differ and no label starts with no-skill; or every label starts with no-skill. That case is kept until classified.
3. Exact one-sided 95 percent bound: when a case has the same pass rate under every label and that rate is 0 or 1, the bound is `1 - 0.05 ** (1/n)`. At rate 0 (0 passes in n runs) it is the one-sided 95 percent upper bound on the pass rate. At rate 1 (n passes in n runs) it is the one-sided 95 percent upper bound on the fail rate. Here n is the smallest scored-run count that any label holds for that case, counting every run file under each label. It is not a sum over labels, so 4 labels of 4 runs give n = 4. The script prints the value as `bound <value>` to 3 places. The exact bound is the exact form of the rule of three; 3/n is its approximation at zero events.
4. A 0-vs-0 or n-vs-n pair is not evidence that the new text keeps the behavior.
5. Every line `eval_grouping.py` prints to standard output is one of these. Each label is quoted as printed:
   - `<path>: error, no verdict`: the script cannot use that run file. This covers a file that is unreadable, is not valid JSON, lacks a cases[] list, holds a case with no string name or no arms.with[] list, holds a record whose passed is not a true or false value, holds a record whose scored is present and not a true or false value, or holds a record whose error is not null. The script prints this line for each such file, then still prints the lines for the other files and cases. In step d.4 the same label marks a case missing from new.json; there the jq join prints it, and the script is not involved.
   - `<case>: separating`: the current skill passes more often than no-skill. The case is kept and goes to the stage rules.
   - `<case>: model default`: no-skill passes at least as often as the current skill. The line carries `bound <value>` and `(not evidence of keeping the behavior)` only at a shared pass rate of 1, because a shared rate of 0 is labeled weak.
   - `<case>: weak`: the current skill passes under 90 percent of runs. The grouping label does not gate; a weak case gets focused cycles (step d.9) only when it is a targeted case.
   - `<case>: no runs under <label>`: the case has no scored run under that label, so it gets no class line.
   - `<case>: unclassified: run no-skill first`: the case has no class yet, in the three situations of item 2 (equal rates with no no-skill label; differing rates with no no-skill label; every label no-skill). When all labels share one rate of 0 or 1, the line also carries `bound <value>` and `(not evidence of keeping the behavior)`. The case is kept until classified.

   `eval_verdict.py` prints these lines:
   - `<case>: p=<value> <verdict>`, with ` confirm=LOSS` or ` confirm=HOLD` appended to a LOSS line when `fresh=` is given and the case is in the fresh file; a LOSS case missing from the fresh file is exit 2.
   - `<case>: dropped N` (candidate), `<case>: dropped N (reference)` and `<case>: dropped N (fresh)`: runs dropped for a non-null error.
   - `<case>: rerun, <n> of <stage> runs after dropped errors`: the candidate has fewer runs than the stage; the script exits 2 after all lines.
   It exits 2, with the message on standard error, for a file that keeps zero runs for a case (reference, candidate or fresh), a candidate with more runs than the stage, a case missing from the reference, a fresh file that does not hold exactly 30 kept runs for a LOSS case, a LOSS case missing from a given fresh file, and invalid arguments.

   `eval_grouping.py` exits 0 when every run file is read, and 1 when any run file has the error label. It exits 2 when the arguments are invalid: no arguments, fewer than two distinct labels (so one label given twice also fails), an argument that is not `label=path`, an empty label, or an empty path. On exit 2 it prints only the usage line `usage: eval_grouping.py label=path [label=path ...]` to standard error; nothing goes to standard output.
6. A model default or weak case carries no stage verdict. Before each ship, run the pre-ship check: `python3 skills/writing-skills/scripts/eval_verdict.py --stage <stage reached> ref=<old.json> cand=<new.json>` on the changed skill's kept cases, at the stage each case last reached, and read each line. Run it once per stage, each time with the candidate file that holds only the cases that last reached that stage (step d.3). When no line prints a LOSS, the command runs without `fresh=` and the ship is not blocked by this check. When a line prints a LOSS, add `fresh=<fresh.json>`, the 30-run confirmation batch of step d.7, and run it again. The script refuses a fresh batch that does not hold exactly 30 kept runs for each LOSS case and a LOSS case missing from the fresh file (exit 2). The `confirm=` value decides a LOSS, and a line with `confirm=LOSS` blocks the ship. Then run the new-model step (section j, item 13), which runs both folders, when the model id or the Claude Code version has changed since its last run. A weak case carries no stage verdict; its focused cycles (step d.9) are the only pass or fail check this procedure gives a targeted weak case.
7. Pool only across grader rounds with identical grader files. The caller chooses the labels, and the script does not check grader files.
8. Make one default-ablation run per case, when a case is first classified or when its grader changes. For a model default case, this default-ablation run is a 30-run skill-on run with `--eval-dir <model-default-dir>` that records the arms named by the case's `skip:` block (`with_skill` and `without_skill`); its saved result file is the reference that the lose-label test of section j, item 13 reads. The new-model step (section j, item 13) is the other run that reads `<model-default-dir>`, as section a, item 3 states. Keep `--ablation none` for comparisons (section d).
9. Cached reference results are keyed by the SHA-256 of the case file hashes, the plugin commit, the model id, the judge model id and the Claude Code version (`cache_key` in `eval_verdict.py`). A cached result is reused until any of those changes, then rerun.

## j. Case, Grader, Judge, Cache and Regression Rules

### Cases

1. A rule gets a case only after a no-skill session first showed its failure. Run 5 runs per situation per arm; count each failure type. Example: 5 no-skill runs, 3 fail at the same step: that failure type has count 3, and the case cites that session.
2. Put every rule in one bin: separating (kept), model default (text deleted, case kept) or weak (no stage verdict; focused cycles when targeted). Section i, item 2 defines the bins.
3. A case prompt names no action. Before any run, a fresh reviewer agent reads the prompt and confirms it names no action. Example: the prompt "Create the worktree for branch feature-x" fails the second reader because it names the action.

### Graders

4. Each case pairs one outcome grader (the end state) with one process grader (how the session got there). Put a never-does-X grader beside a positive grader for the same behavior.
5. A grader never copies a string from a run output. Hash the case files (`prompt.md`, `graders/*.md`, `case.yaml`, `scaffold.sh`); the hashes feed the cache key (section j, item 9).
6. A grader counts only after it passes a saved current-skill session and fails a saved no-skill session.

### Judge

7. A model judge reads a short final answer or one file and returns pass or fail. Pin its tier, the same on both checkouts.
8. A judge blocks a merge only after it agrees with 27 of 30 owner-labeled passes and 27 of 30 owner-labeled fails. Fewer on either side and the judge does not block.

### Cache and recorded fields

9. A cached result is reused until the cache key changes (section i, item 9). The cache key is the SHA-256 of the case file hashes, the plugin commit, the model id, the judge model id and the Claude Code version, as computed by `cache_key` in `eval_verdict.py`.
10. A case the current skill passes in under 90 percent of runs is weak and carries no stage verdict. Example: a cached result of 26 of 30 (86.7 percent) with an unchanged case hash is reused, and the case is weak: it gets focused cycles (step d.9) only when targeted.
11. Record with each result: the model, the harness, the prompt and the permissions. The run's model id and the judge model id go in the record as fields, not in this file.
12. A run with a non-null error is dropped before counting and rerun.

### Regression

13. New-model step. Run this step when the model id or the Claude Code version changes. It runs both folders: `<model-default-dir>` (passed with `--eval-dir`) and the default folder `<default-dir>`, which is the everyday set. Run both arms, 15 runs each, as section e, item 1 defines them, on each folder; section i, item 1 places the no-plugin records under `arms.with`. A skip test (`bin: model default`) that is under 15 of 15 without the skill gets a 30-run check; it loses its label if the drop stands, meaning that check is a LOSS under the stage-30 rule of step d.6, with the reference being the saved result file of the default-ablation run (section i, item 8), read by `eval_verdict.py` as the with-skill arm under `arms.with`, and the candidate being the cumulative runs of step d.3, and one standalone line goes back into the skill, recorded next to that case. A kept test (a case the separating label of section i, item 2 has kept in step d, and that is not weak or unclassified) that is at 15 of 15 without the skill is reported to the owner as a skip candidate; its label is not changed. A passing skip case gets no line.
14. Record preflight before each paid batch, as section k, item 3 states.

## k. Rebuild, Size Report and Preflight

1. Start a rebuild with an empty skill body and the description unchanged. Run each kept case against the cached reference in the stages of step d.6. Add a line only for a case that fails the reference. Each added line is a standalone unqualified rule that fixes the lowest-passing case, with no condition that points at another line. Record the line in the rebuild log next to its case. A case that passes gets no line. A line is added to the empty skill body. After it is added, rerun the focused 5 runs of its case; the next line is added only when that case is NEXT at 5 of 5. Example: after a line is added for case A, case A's focused 5 runs are rerun, and a line for case B waits until case A is NEXT at 5 of 5.
2. Report the on-invoke size before and after the rebuild: tokens and bytes for each, and the cut in percent. The report states no pass or fail on the cut. Example: a 70 percent cut is shown as 70 percent, with no pass or fail. Keep the hook text unchanged during the rebuild. State in the report that the result holds for the current hook text and model tier.
3. Before each paid batch, record free disk, free inodes, login and the usage limit. If free inodes is zero, the batch does not start, and the record shows 0.
